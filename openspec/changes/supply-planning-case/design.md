# design — supply-planning-case

## D1：資料來源與授權

- 來源：GitHub `CIOL-SUST/SupplyGraph`（Wasi et al., 2024, arXiv:2401.15299），`Raw Dataset/Homogenoeus/` 下的 Temporal Data（Unit／Weight 各四檔）與 Nodes。
- **不 vendor 原檔**：上游 repo 授權為 LGPL-2.1，且可穩定重抓。`src/data.py` 內釘每個檔案的 URL 與 sha256，下載到 `data/raw/`（gitignored）。
- 為什麼不用 DataCo（Mendeley，CC BY 4.0）：月筆數平到約 5,200、2017-10 腰斬，看起來是合成資料；`Late_delivery_risk` 完全由實際與預定運送天數決定，拿來做分類就是洩漏。為什麼不用 M5：零售、規模太大，且 Kaggle 需要帳號。

## D2：資料模型

長表 `flows`：`date (datetime64), sku (str), flow ∈ {order, production, factory_issue, delivery}, qty_unit (float), qty_ton (float)`。

- 上游欄名對映：`Sales Order` → order、`Production` → production、`Factory Issue` → factory_issue、`Delivery To distributor` → delivery。
- SKU 主檔 `skus`：`sku, group, subgroup, ton_per_unit`。`ton_per_unit` 取兩種單位都非 0 的列的噸／件比中位數；實測每個 SKU 的比值固定（相對差 < 1e-13），品質檢核守住這件事。
- **`qty_ton` 一律由件數 × `ton_per_unit` 重算**，上游原值留在 `qty_ton_reported`。原因：上游噸數版有缺欄（POV005L04P 的工廠出庫噸數整欄為 0）；整欄缺只報告，部分缺才算硬錯誤。
- **共用代碼**：上游有兩個不同的 SKU 都叫 POP001L12P，流量檔把第二個寫成 `POP001L12P.1`（四條流量數值都不同，不是重複列），主檔則列兩次同名。照流量檔命名對齊；`POP001L12P.1` 沒有廠別對照。
- 廠與儲位對照 `sku_sites`：去重後 277 列，一個 SKU 對 1–13 個廠。**生產量只有 SKU 層級、沒有分廠**，所以 M4 的產能限制不能逐廠設定（見 D6）。

## D3：品質檢核的定位

品質檢核輸出一份 dict（落盤 `results/m0_quality.json`），**只報告、不修資料**。理由：這份資料的「怪」大多是資訊不足（期初庫存、期初欠貨、週末），不是錯誤；修掉會把限制藏起來。硬錯誤只有：sha256 不符、日期不連續、負值、件數與噸數不對齊、噸／件比不固定、同一條流量部分缺噸數。遇到就中止。

已知怪處（下載後實測，結論以 `results/m0_quality.json` 為準）：週五訂單近 0（推測為當地週末）；約 11% 的產品日累計出貨超前累計訂單；倉庫流量（累計出庫 − 累計出貨）會掉到負值；約四分之一的 SKU 有 ≥ 98% 的天數為 0。

## D4：KPI 定義

| KPI | 定義 | 為什麼這樣定 | 為什麼不是另一個 |
|---|---|---|---|
| fill rate | min(Σ出貨, Σ訂單) ÷ Σ訂單（逐 SKU，再以噸數加權彙總） | 最直接的 in-full | 不用逐日平均：大量的日子與少量的日子權重會一樣 |
| OTIF 代理 | FIFO 把出貨分配給訂單批，D 天內交齊的批數比例；報 D = 0…7 曲線 | 沒有逐單交期，只能用「下單後幾天交齊」代理準時 | 不挑一個 D 當唯一答案：D 是假設，曲線才誠實 |
| 期初欠貨 | 下限 = max(0, max_t(累計出貨 − 累計訂單)) | 出貨超前訂單，代表期初有舊單在消化 | 不假設 0：會讓新訂單的延遲看起來比實際短 |
| 缺貨率 | 存在超過 D 天未交齊訂單批的產品日 ÷ 有效產品日 | 計畫員看得懂的「有沒有斷貨」 | 不用「庫存 = 0 的天數」：期初庫存未知，庫存只算得出下限 |
| 庫存天數 | （期初庫存下限 + 累計工廠出庫 − 累計出貨）÷ 近 28 天平均日訂單 | 與 DIO 同義、單位是天，非專家看得懂 | 不用金額版 DIO：沒有成本資料 |
| ABC × XYZ | ABC 用噸數累計 80%／95%；XYZ 用週需求 CV 0.5／1.0；休眠 = 零值日 ≥ 98% | 用噸數，不同包裝規格才能比；用週不用日，避開週五為 0 造成的假波動 | 不用件數：一件 2 公升和一件 25 公斤不可比 |
| WAPE／bias | WAPE = Σ\|e\| ÷ Σ實際；bias = Σ(預測 − 實際) ÷ Σ實際 | 間歇需求下 MAPE 會除以 0 | 實際全 0 時回 NaN，不回 0（回 0 會把沒有需求的 SKU 算成完美預測） |

## D5：程式結構

- `src/data.py`：下載、驗 sha256、讀寬表、轉長表、SKU 主檔。
- `src/quality.py`：純函式檢核，輸入長表，輸出 dict。
- `src/kpi.py`：純函式 KPI，輸入 numpy／pandas 序列，不碰檔案。
- `scripts/run_m0_m1.py`：串起來，寫 `results/m0_quality.json`、`results/m1_kpi.json`、`results/m1_sku_table.csv`。
- 測試只吃人工構造的小序列（手算得出答案），所以 CI 不需要資料、離線可跑。另有 claim-discipline 一關，檢查 README 的數字仍與 `results/*.json` 一致。

## D6：M2–M5 的待定事項（開工前補附錄）

- M4 產能：生產沒有分廠，先以「產品群」當產線代理，產能 = 該群歷史週產量（噸）的 p95。開工前用資料確認產品群與廠的對應是否夠乾淨；不夠乾淨就改成單一總產能。
- M3 前置期：從生產與出庫的時間差估，估不出來就用參數掃描（1–7 天）。
- M5 標籤：以 M1 的缺貨定義往前看 7 天，特徵只能用當天以前的資料。

## D7：M2 需求預測（附錄，2026-10-20）

**預測對象**：每個有效 SKU（32 個）的**每日訂單量**（件數）。用訂單不用出貨：出貨會被缺貨截斷，拿出貨當需求會把過去的缺貨學進預測裡。評估時把件數換成噸數再彙總，不同包裝規格才能加總。

**回測設計**：rolling origin，起點從第 112 天（2023-04-22，16 週訓練）開始，每 7 天一個，共 15 個起點；每個起點預測後 1–7 天。每個起點只用起點當天以前的資料，模型每個起點重訓。
- 為什麼不用單一切點：221 天只有一個切點的話，結果會被那一週的事件綁架（例如節日週）。15 個起點可以算出方法差距的雜訊帶。
- 為什麼不用更多起點：訓練期少於 16 週時，週別特徵只有不到 16 個樣本。

**資料裡的事件**（下載後實測週總噸數）：2023-04-23～29 那週 1,837 噸、2023-06-25～07-01 那週 1,593 噸，平常週約 3,000～5,000 噸。時間點對得上當年的開齋節與宰牲節（日期以公開假期表核對後寫進程式，不憑記憶）。另有 3 月後的下降趨勢。
- 節日是計畫員事前就知道的事，所以把**已公告的假期**當特徵不算洩漏。LightGBM 做兩版：有假期特徵、沒有假期特徵；差距就是「把行事曆給模型」的價值。
- 回測指標同時報「全部起點」與「排除節日週的起點」，避免一個方法只靠節日週贏或輸。

**方法**：

| 方法 | 內容 | 為什麼放 |
|---|---|---|
| 季節 naive | 上週同一天 | 最低標，週五為 0 這種規律它免費就學到 |
| 星期平均 | 近 4 週同一星期的平均 | 比季節 naive 穩，計畫員常用的手算法 |
| 移動平均 28 | 近 28 天平均，不分星期 | 對照：證明星期效應真的重要 |
| ETS | statsmodels Holt-Winters，加法季節 7，阻尼趨勢 | 經典統計方法 |
| Croston／TSB | 間歇需求專用，出在每天的平均；乘上星期比例還原星期型態 | 驗證 H2 前要先知道間歇 SKU 用專用方法有沒有比較好 |
| LightGBM 全域 | 一個模型學全部 SKU；目標除以起點前 28 天平均（尺度歸一），objective = L1（對齊 WAPE） | 表格 ML 做預測，業界主流 |

LightGBM 特徵（全部在起點當天就算得出來）：預測日的星期、horizon h、同一星期近 1／4 週的值、起點前 7／28 天平均、起點前 28 天零值比例、產品群、SKU 代碼、假期旗標（僅有假期版）。訓練樣本：訓練期內每一天都當一次起點、每個 h 各一列，目標日必須 ≤ 外層起點。

**評估**：WAPE 與 bias，以噸數彙總；分 ABC×XYZ 群、分 horizon 報。方法比較用 15 個起點的成對差：報差距中位數、勝場數與 Wilcoxon 符號秩檢定。贏不過星期平均就照寫。

**輸出**：`results/m2_forecast.json`（彙總）、`results/m2_backtest.csv`（每個起點 × SKU × 日的實際值與各方法預測，M3 用來抽殘差）。

**不做**：GNN（上游論文的主題，與決策問題無關）、深度學習（221 天不夠）、外部變數（沒有價格與促銷資料）。

## D8：M3 庫存政策模擬（附錄，2026-10-20）

**要回答的問題**：H1（選服務水準目標 vs 選預測模型，哪個對庫存與缺貨影響大）與 H2（常態近似的安全庫存對波動 SKU 保護不足）。

**主模擬＝歷史重播，不是合成需求**：需求一律用實際訂單逐日重播，預測一律用 M2 回測裡各方法的真實預測。理由：要比較「換模型」與「換目標」，所有組合必須面對同一條需求路徑；用「預測＋bootstrap 殘差」生成需求的話，需求會隨方法而變，比較就不公平（原 US-004 寫法的修正）。Monte Carlo 用在兩處：前置期的隨機延誤，以及對 SKU 做 bootstrap 求差距的信賴區間。

**前置期**（下載後實測，逐 SKU 交叉相關最佳時差）：生產→工廠出庫 0～1 天、出庫→出貨 0 天、訂單→出貨 1～2 天。名目前置期取 L = 2 天，掃描 {1, 2, 3, 5, 7}。

**模擬機制**（每 SKU 一個倉，逐日）：
1. 當天先收到到貨，再依先進先出出貨：先補舊欠單，再出當天訂單。當天訂單當天出完的量算進 fill rate（type 2，教科書的 fill rate）。
2. 日終若是檢視日就下單；到貨日 = 下單日 + 實際前置期。
3. 起點：第 5 個 M2 起點（2023-05-20，前 4 週的誤差用來估第一次安全庫存）；期初在手 = 第一次的 S、無在途。量測到最後一個預測窗結束（2023-08-05），共 11 個週期。

**兩種政策**：
- **(R,S)**：每 7 天（M2 起點日）檢視；下單量 = max(0, S − 庫存位置)，S = 未來 R+L 天預測和 + 安全庫存。
- **(s,S)**：每天檢視；庫存位置 ≤ s 時補到 S。s = 未來 L 天預測和 + 安全庫存，S = s + 未來 7 天預測和（一週當最小批量的代理）。
- 預測只到起點後 7 天；超過 7 天的部分沿用同一週的星期型態（循環）。

**安全庫存**：SS = q × 尺度 × √((R+L)/7)。尺度 = 起點前 28 天平均日需求 × 7（起點當天已知，避開除以極小預測的爆量）。q 來自週誤差 r = (實際週和 − 預測週和) ÷ 尺度，**只用該起點以前的起點**，依 X 與 Y＋Z 兩群合併（單一 SKU 只有 4～14 個點，估不出 98% 分位數）。三種 q：
- `normal_classic`：z_α × σ（教科書公式，假設預測無偏）
- `normal`：μ + z_α × σ（把 bias 補回來）
- `empirical`：r 的 α 分位數

`normal_classic` 對 `normal` 的差＝修正 bias 的價值；`normal` 對 `empirical` 的差＝分佈形狀的價值（H2）。下載後實測：星期平均的週相對誤差偏態 X 群 1.09、Y 群 5.45，H2 的前提成立，結論看模擬。

**目標**：α ∈ {0.80, 0.85, 0.90, 0.95, 0.98, 0.99}，指週期服務水準（CSL：一個週期內不缺貨的機率）。

**KPI**：fill rate（噸數加權）、達成 CSL（11 個週期中不缺貨的週期比例）、庫存天數（平均在手噸 ÷ 平均日需求噸）、缺貨日比例。

**H1 怎麼判**：固定預測方法＝星期平均、(R,S)、empirical，目標 0.80→0.99 時庫存天數與 fill rate 的變化幅度；對照固定目標 0.95 時各方法之間的差距；再用內插比較「達到 fill rate 0.98 需要幾天庫存」在方法之間差多少（原訂 0.95；第一次實跑發現多數方法在 α = 0.80 時 fill rate 已超過 0.95，內插不到，改用每條曲線都跨過的 0.98）。bootstrap 的 replicate 只要有一個方法內插不到就整個作廢，作廢比例寫進結果；作廢超過 10% 不判 H1。差距對 SKU 做 bootstrap（1,000 次）給 95% 信賴區間。

**H2 怎麼判**：(R,S)、L = 2、星期平均，比較 normal 與 empirical 在 X 群與 Y＋Z 群的「達成 CSL − 目標」。若 normal 在 Y＋Z 群的短缺明顯大於 X 群，且 empirical 把短缺縮小，H2 成立；否則照寫不成立。

**Monte Carlo**：基準組合（星期平均、(R,S)、empirical、全部目標）下，實際前置期 = L + U{−1, 0, +1}（不低於 1），200 個種子，報 KPI 的 5%／50%／95% 分位數。

**輸出**：`results/m3_policy.json`（彙總與 H1、H2 判定）、`results/m3_grid.csv`（每個組合一列）。

**實跑結果摘要（2026-10-20，數字以 `results/m3_policy.json` 為準）**：H1 成立（目標 0.80→0.99 多 22.3 天庫存；等服務下方法間差 2.8 天；差距的 95% 區間 10.5～40.1 天）。H2 不成立：常態近似對 Y＋Z 群反而多保護約 3 個百分點，對 X 群短少約 2～3 個百分點；經驗分位數也沒有改善 X 群。推測原因是 Y＋Z 合併誤差被少數極端週撐大、X 群的誤差分佈在 11 週內不穩定，留待 README 限制段說明。

## D9：M4 產能排程 MILP（附錄，2026-10-21）

**要回答的問題**：換線（setup）次數與庫存之間怎麼取捨？實際的生產節奏落在這條取捨線的哪裡？

**資料實測（決定建模方式）**：
- 生產幾乎每天都有：主力 SKU 221 天裡有 150～190 天在生產，每天每群平均 2～5 個 SKU 上線，像是接單後小批量生產。
- 廠別對照不是產線：19xx 廠同時出 A／M／S 群、21xx 廠同時出 S／P 群，一個 SKU 對到 12～24 個廠，比較像出貨或儲位點。所以**不按廠設產能**。
- 改以**產品群當產線代理**（A、M、P、S 四條），產能 = 該群歷史週產量（噸）的 p95：這是假設，README 要寫明。實際週產量平均 A 704、M 154、P 448、S 2,351 噸，與週訂單量相當。

**模型**（週為時間桶，量測期與 M3 相同：2023-05-21 起 11 週）：

變數：x_it 生產噸數、y_it ∈ {0,1} 是否開線、I_it 期末庫存、B_it 期末欠單。

- 平衡：I_{i,t−1} − B_{i,t−1} + x_it − d_it = I_it − B_it
- 產能：Σ_{i∈群 g} x_it ≤ Cap_g
- 開線連結：x_it ≤ Cap_g · y_it
- 最小批量：x_it ≥ m_i · y_it，m_i = 該 SKU 歷史生產日的中位批量（噸）
- 期末條件：I_iT − B_iT ≥ 實際計畫在期末的淨庫存（讓 MILP 不能靠把庫存吃光來省成本，兩者期末位置相同才可比）
- 目標：min Σ h·I + Σ p·B + Σ s·y；h = 1（每噸週），p = 10，s 為換線成本，掃 {0, 1, 2, 5, 10, 20, 50, 100, 200}

期初淨庫存：用 M1 的方法重建（期初下限 + 累計生產 − 累計訂單，算到量測起點前一天），標示為下限；MILP 與實際計畫用同一個期初值。

**兩種跑法**：
1. **完全資訊**（需求 = 實際週訂單）：掃 s 得到「換線次數 × 平均庫存」的取捨線，再把實際生產計畫放上同一張圖。這是排程本身能做到的上限，不是預測加排程的實戰成績，README 要分開講。
2. **滾動計畫**（需求 = M2 星期平均的週預測）：每週以 4 週為期解一次，第 2～4 週沿用同一週預測，只執行第 1 週，再用實際訂單結帳。s 固定為 20（事前選定，不看結果挑）。跑兩版：不帶安全庫存，以及帶 M3 基準的安全庫存（empirical、α 0.95，作為軟下限，缺口每噸週罰 2）。報實現的欠單、庫存、換線次數，與完全資訊和實際計畫並列。

**排除**：SO0002L09P 有訂單但整段期間沒有任何生產紀錄（可能外購或他廠供應），不在這些產線上，排除在 M4 之外。

**解題器**：HiGHS，經由 `scipy.optimize.milp`（原訂 PuLP＋CBC；2026-10-21 實測 PuLP 4 改了 API 且不再附 CBC，PuLP 2.x 附的 CBC 只有 x86_64 執行檔，在 Apple Silicon 上跑不起來。scipy 已是依賴，CI 也不必另裝）。每次求解設時間上限 60 秒與 MIP gap 0.5%，結果記錄求解狀態與 gap；非最優解要在結果裡標出來。

**為什麼不用其他做法**：日別 MILP 有 32 × 77 個二元變數，CBC 解得出來但太慢，也無法掃參數；週別與計畫會議的節奏一致。不做多廠配置：資料沒有分廠的生產量。

**輸出**：`results/m4_schedule.json`（取捨線、實際計畫位置、滾動計畫 KPI、求解狀態）、`results/m4_frontier.csv`。

**實跑結果摘要（2026-10-21，數字以 `results/m4_schedule.json` 為準）**：11 次取捨線求解全部最優。實際計畫是 283 個開線週、平均淨庫存 4,339 噸（期初為下限）。完全資訊、s = 20 時 183 個開線週、1,397 噸，但這是知道未來需求的上限。用預測滾動、不帶安全庫存時，平均欠單 476 噸／週；帶 M3 安全庫存後欠單降到 26 噸，庫存升到 5,092 噸，總成本仍高於實際計畫。結論：這家工廠逐日小批量、接單後 1～2 天出貨的節奏，用週桶加預測的 MILP 打不贏；MILP 的價值在量化「少換一次線要多放多少庫存」，不在取代現行排程。
